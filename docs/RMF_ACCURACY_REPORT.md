# RMF Accuracy and Usability Improvements – release report

Product name in the UI remains **IronVision AI**; the user's document refers to "AegisRMF", and no branding was changed. No modules were rebuilt, renamed or removed. Auth/deploy configuration, the Droplet and production were not touched.
Regulatory interpretations are recorded in `docs/RMF_INTERPRETATION_DECISIONS.md`.

## Per-finding summary
| # | Finding | Status | What changed |
|---|---|---|---|
| 1 | Registration roles | Implemented + tested | AODR, CCP and User Representative are removed from the **registration role picker only** (`registration: false` on the role reference). New registrations that send them are rejected with 422. They remain in the model and DB: CCP in Inheritance and AODR in Authorize. On other screens they are labelled "(not assigned at registration)". RBAC unchanged. |
| 2 | Categorization redesign | Implemented + tested – **SME review** for CNSSI baseline tables | Step 1: framework guidance plus "Is this a National Security System?" Yes/No/Unsure (44 U.S.C. §3552, SP 800-59). Steps 2–4: 800-60 types → C/I/A with adjustments + justification → calculation. FIPS 199 uses the high-water mark and the 800-53B baseline. CNSSI 1253 keeps **C, I and A separate** (M-H-L, no overall value) and its baseline selection is labelled "SME review required". Step 5: rationale + **AO approval**, revision history, and pending re-approval when inputs change (the approved values stay in force). Existing categorizations are migrated as revision 1 `legacy_unreviewed`. |
| 3 | Authorization Type Sought | Implemented + tested | Removed from registration (422 if sent) and moved to **6 · Authorize** (authorization strategy) next to the AO decision. Editable only by roles with `system.write`, with a required reason and an audit event. Existing values are preserved and shown. |
| 4 | Privacy Threshold Analysis | Implemented + tested – **SME review** for question wording | Configurable, versioned question sets (agency sets are admin-defined). The default set is labelled "Example set – validate against your agency's privacy requirements". Answers are Yes / No / Not sure, follow-ups are conditional, explanations are stored, and flags mark answers needing privacy review. The outcome is **always a recommendation**: a single No never concludes "no PIA required". A new additive **Privacy Official** role/persona (`privacy.review`) approves or returns a PTA (reviewer, date, status, rationale). History is kept. |
| 5 | Parameter Comparison CSV empty | Implemented + tested | **Root cause:** the old export listed only policy values and approved system ODP values, so a system without a linked policy or ODP values produced a header-only file; catalog ODPs were never included. **Fix:** one service builds the rows from the catalog ODPs of the system's assigned controls next to the policy, system ODP and overlay values. That service feeds the on-screen table (Select step), the system CSV (Workbench header / Select) and the policy CSV (policy detail). Filters, system scope and RBAC apply. The CSV is UTF-8 with BOM, protected against formula injection (`= + - @ tab CR` → apostrophe prefix) and properly quoted. With no matching rows the server returns 204 with a reason and the UI shows a message instead of downloading an empty file. **Omitted column:** "Baseline value" – SP 800-53B assigns no ODP values (documented in the API and UI). |
| 6 | Overlays | Implemented + tested | Each overlay shows its issuing authority, source document, framework, status, effective date and applicability. CNSSI overlays are offered only to CNSSI 1253 (NSS) systems. **Classified overlay** requires an explicit Yes to "processes classified information" (App. E Att. 5 §3 p. 3) and is never applied from a level alone. Restricted overlays show "Unavailable – pending validation". Admins can record agency overlays (metadata). Existing selections are kept and flagged "Applicability review needed". |
| 7 | Privacy overlay / ACCT | Implemented + tested | "ACCT" **is** in the source (CNSSI 1253F Att. 6 Table 1 p. 11; Question 2 p. 12), so it is kept, cited and NSS-only. FIPS systems are told that privacy controls come from the **SP 800-53B privacy baseline** via the PTA/PII determination. Privacy determinations need Privacy Official approval. The UI states AI is suggestion-only for privacy. |
| 8 | Yes-only controls | Implemented + tested | Screens fixed: **registration** PII (Yes / No / Unknown – requires review, stored as NULL + `pii_status=unknown`, distinct from No and from unanswered, and required on submit); **Categorize** PII (same) plus the new NSS (Yes/No/Unsure) and classified-information (Yes/No/Unknown) questions; **PTA** (Yes/No/Not sure, required questions enforced, conditional follow-ups update when an answer changes); **overlay applicability** (driven by the explicit classified answer). Audited and left unchanged, because they are on/off settings or selections rather than questions: Select "include privacy baseline" toggle, notification preferences, AI use-case toggles, connector enable/disable. |
| 9 | IL6 / operating environment | Implemented + tested | The SRG impact level picker appears only for cloud models. IL6 only when CNSSI 1253 + classified = Yes, otherwise disabled with the reason. On-prem shows "SRG impact levels apply to cloud service offerings". The backend rejects inconsistent new values (422). Existing values are kept and flagged "Review applicability". |
| 10 | Evidence actions | Implemented + tested | The Actions menu offers View, Download, Replace, Upload new version, Version history and Remove. A new version is immutable: the old object and SHA-256 are kept and the latest becomes active. A reason is required, type/size validation and the existing scanner hook run, and dependent evidence→control mappings and TR rows are flagged "Evidence changed – re-review". Remove is **logical** (confirmation + reason) and is blocked while a **legal hold** is set (admin-only toggle). Mappings are closed, not deleted, so history still resolves. **Permanent deletion is not offered.** Historical versions are visible only to evidence submitters, assessors and auditors. Every action is audited. |
| 11 | Side-by-side mapping review | Implemented + tested | Available in the Policy Auditor detail and from the Mapping Review queue. **Left (sticky on wide screens):** control ID/title, statement, enhancements, ODPs, CCIs/objectives, supplemental guidance (shown separately). **Right:** policy name/version, excerpts **verified server-side as exact substrings**, highlighted in context with section/page, confidence + explanation, rationale, coverage, gaps. Accept / Reject / Edit mapping / Request reanalysis / Flag for manual review / Override coverage, each with a comment, persisted and audited. |
| 12 | Confidence and citations | Implemented + tested | Every mapping shows an exact, located excerpt or "No supporting text found – manual review required". Evidence-based confidence follows the legend: explicit ID + requirement language = High, requirement language only = Medium, inferred = Low. Each mapping is marked direct or inferred. Coverage outcomes map Fully/Partially/Not Addressed/Requires Manual Review onto MET/PARTIAL/MISSING; confidence never makes a mapping Fully Addressed. The gap analysis lists missing requirements, incomplete statements, unsupported claims, ODPs not set, and items labelled "Recommendation". Overrides need a justification. Reanalysis never overwrites approved decisions; it stores a proposal marked "differs from approved". **Root cause of missing excerpts:** manual mappings were saved as **High** with no snippet. They now take the evidence the text actually contains, or Low with an explicit no-text flag. |

## Limitations
- SP 800-60 catalog: 168 types with provisional impacts but **no type descriptions** in our extract, and **agency-specific information types are not implemented**.
- Agency overlays are metadata records; applying their control changes is not implemented.
- Policy excerpt page numbers appear only when the stored text has page breaks (the current extraction has none, so the UI says "Page not available"). The section comes from the nearest heading (heuristic).
- Evidence `expires_at` exists but is not yet populated automatically; the freshness window still drives staleness. The Mapping Review queue does not yet list evidence revalidation flags; they show on the evidence record, its control mappings and TR rows.
- Stored mapping confidence is kept for compatibility; the evidence-based confidence is computed and shown alongside it.

## Docker
There is no Docker daemon in this environment, so **Docker builds were not run or confirmed here**. Build and verify on the Droplet (documented flow in `docs/DIGITALOCEAN_DEPLOYMENT.md`):
```bash
cd /opt/ironvision/IronVision-AI
git status                       # 1. must be clean (no local edits) before pulling
git log --oneline -1             #    note the current commit for rollback
git pull                         # 2. fast-forward to this release
./deploy.sh                      # 3. demo deploy: builds the images, runs the `migrate` service (alembic upgrade head 0023 → 0026), starts the app, ends with "Ready: https://<APP_DOMAIN>"
docker compose -f deploy/digitalocean/docker-compose.do.yml --env-file deploy/digitalocean/.env.production run --rm --no-deps migrate alembic current   # expect 0026 (head)
curl -fsS https://demo.ironvisionai.com/api/health
```
If the deploy fails, `deploy.sh` prints `#### DEPLOYMENT FAILED at step "<step>"`. Migrations are additive; rollback is `git checkout <previous commit>` + `./deploy.sh` (the 0024–0026 downgrades exist and were verified on a database copy, but are not needed for an app rollback because the old code ignores the new tables/columns).
