## 3. Mocked or simulated (shown and labelled)

- **Live API connectors** on Evidence Sources: the page itself says "In this deployment these connectors are MOCK/DEMO adapters". The narration says they are mocked.
- **eMASS sync**: the POA&M page header shows "eMASS: MOCK eMASS (synthetic demo connector – no real eMASS contacted)". The narration says "mocked eMASS connector".
- **Authentication**: the header badge "DEV AUTH – SIMULATED, NOT CAC/PIV" stays visible. Persona approvals are labelled "simulated signature – not CAC/PIV".
- **Personas**: one presenter switches between ISSO, ISSM, SCA and AO personas, which is the sandbox "same person" mode. The narration states that in a real organization a different person is required.

## 4. Claims deliberately not made

- No FedRAMP authorization, and no ATO for IronVision itself.
- The narration never says AI approves, assesses or authorizes. Every decision point shows a human role.
- TR/HW-SW workbooks are described as "eMASS-formatted … designed to preserve the template". Excel and eMASS import compatibility is **pending human verification** and is not claimed.

## 5. Substitutions and differences vs. the whitepaper

| Requested element | What is shown instead / why |
|---|---|
| "System registration" with submission | The form is filled in (name, key roles, NSS question) but **not submitted**, so the shared demo is not polluted. The pre-created NSS example system "Tactical Edge Gateway (TEG)" is used for CNSSI |
| CNSSI 1253 NSS system | The shared demo seed has no NSS system. A **synthetic** TEG system (CNSSI 1253, M-H-L, PII = yes) was created in the demo tenant through the public API before recording |
| AO approval of categorization | Shown indirectly: the approval was performed through the API (AO persona) before recording. On screen the approved M-H-L values and the resulting CNSSI baseline are visible, and the narration states that the AO approved |
| ISSM endorsement | Performed through the API before recording (ISSM persona). The video shows the AO decision form that only appears after endorsement |
| STIG / ACAS ingestion | Existing completed ingest runs of the seeded sample `.ckl` and `.nessus` files are opened. No new upload is performed during the recording |
| Risk acceptance | The package shows the "Risk acceptances" panel (none yet). No risk acceptance is created |
| Test Results workbook | The blank eMASS TR template (test fixture) was imported into LTP and rows were generated by the real worker job before recording |
| CISA KEV / critical vulns | Shown via the Portfolio KEV card, the Monitor "Open CAT I / KEV" card and POA&M P-0015 (Log4j CVE-2021-44228, CISA KEV) |

The whitepaper and the app agree on every feature shown. No whitepaper capability is shown in a stronger form than the app implements.

## 6. Defects found while preparing the recording (fixed, not hidden)

1. **TR generation crashed** when a control had a POA&M (`'Poam' object has no attribute 'title'` in `backend/app/services/tr/service.py`). Fixed by using `human_id` + `weakness`, and the TR test suite passes (27).
2. **The AI implementation draft vanished ~1 s after it appeared.** A quiet data refresh after the POST reset the editor state. Fixed in `ImplementationPanel.tsx`: the editor now resets only when the control or its latest saved version changes.

## 7. Synthetic records added to the shared demo tenant for the recording

- System **TEG – Tactical Edge Gateway** (synthetic NSS), with role assignments copied from LTP, categorization revision 2 (M-H-L) approved by the AO persona, and the CNSSI 1253 baseline.
- **LTP**: blank eMASS TR template imported and rows generated; AI evidence analysis for rows 41–42; authorization package R-0001 submitted and ISSM-endorsed.
- All of these are audited. The demo tenant resets nightly, so the reset removes them. `scripts/demo_video/prep_demo_data.py` recreates the base records.

## 8. Recording limitations

- Headless Chromium has no OS cursor or native dropdown pop-ups. The cursor is an overlay, and `<select>` changes appear as instant value changes.
- Wait times (page loads, the live AI call, persona switches) are cut, so the on-screen app is faster than real time in those places.
- Video timing was fixed at recording time, and the narration blocks were then aligned to the recorder's event log (≤ 2.55 words/s per block, ≈ 140–150 wpm).

Reproduce: `python3 scripts/demo_video/prep_demo_data.py` → `python3 scripts/demo_video/record_demo.py` → `python3 scripts/demo_video/assemble.py` → `python3 scripts/demo_video/build_docs.py`.
